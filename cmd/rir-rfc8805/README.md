# rir-rfc8805

Experimental CLI for enriching RFC 8805-style geofeed CSV rows with RDAP-derived RIR and network metadata.

This is research code, not a production pipeline. It exists to answer questions like:

- Which RIR serves RDAP for each advertised geofeed prefix?
- Does the RDAP bootstrap RIR differ from the final RDAP responder?
- Which RDAP `networkName` values dominate each RIR's geofeed footprint?
- How concentrated or long-tailed are geofeed-published networks by RIR?

## Current State

`main.go` is a single-file Go command. It currently:

- Reads a CSV input and treats the first column as an IP prefix.
- Queries RDAP for the first address of each prefix.
- Emits one JSON object per input prefix to stdout.
- Writes progress, cache statistics, and row-error counts to stderr.
- Preserves per-row lookup failures as JSON rows instead of aborting the whole run.
- Uses a bounded worker pool so fast RDAP lookups keep flowing while slower lookups wait or time out.
- Tunes the HTTP transport's idle and per-host connection pools from `-max-concurrent-rdap`.
- Uses `github.com/kenshaw/diskcache` for exact on-disk HTTP caching of successful RDAP responses.
- Optionally uses a semantic trie cache to reuse an RDAP network result for later query IPs inside the returned RDAP network range.
- Uses `go4.org/netipx` to convert RDAP start/end address ranges into covering prefixes for the semantic cache.

The command is intentionally lightweight: no subcommands, no database dependency, no persistent run manifest, and no built-in summarization. Downstream CSV and Markdown views are generated by separate ad hoc scripts.

Output order is completion order, not input order. Each JSON object carries the original CSV `row`, `prefix`, and `queryIp`, so downstream analysis should key on those fields rather than line position.

## Build

Run from the repository root:

```bash
go build -o rir-rfc8805 ./cmd/rir-rfc8805
```

## Example Runs

Small smoke run:

```bash
./rir-rfc8805 \
  -input ~/tmp/validated-all.csv \
  -limit 1000 \
  -progress-every 100 \
  > /tmp/rir_1000_stdout.jsonl \
  2> /tmp/rir_1000_stderr.log
```

Sampling run for per-row network-name analysis:

```bash
./rir-rfc8805 \
  -input /tmp/validated-noafrinic-shuffled.csv \
  -limit 100000 \
  -semantic-cache=false \
  -max-concurrent-rdap 8 \
  -rdap-timeout 8s \
  -progress-every 1000 \
  > /tmp/rir_local_100k_stdout.jsonl \
  2> /tmp/rir_local_100k_stderr.log
```

Large remote collection example:

```bash
./rir-rfc8805 \
  -input geofeed-prefixes-shuffled.csv \
  -semantic-cache=false \
  -max-concurrent-rdap 8 \
  -rdap-timeout 5s \
  -progress-every 5000 \
  > rir_stdout.jsonl \
  2> rir_stderr.log
```

Very high-concurrency runs may finish quickly but can produce higher RDAP row-error rates. Use them for stress-testing, not as the default evidence source for analysis.

For long remote runs, launch outside the SSH session with `nohup` and save a PID file. The command itself does not yet create status files or support resume.

## Flags

| Flag | Default | Meaning |
| --- | ---: | --- |
| `-input` | `~/tmp/validated-all.csv` | CSV input path. The first column must be parseable by `netip.ParsePrefix`. |
| `-cache-dir` | user cache dir under `rir-rfc8805/rdap-http` | Persistent exact HTTP cache directory. |
| `-limit` | `0` | Maximum number of CSV rows to process. `0` means all rows. |
| `-max-concurrent-rdap` | `5` | Worker count and maximum in-flight RDAP lookups. Values below `1` are coerced to `1`. |
| `-rdap-timeout` | `30s` | Timeout for one RDAP request. |
| `-progress-every` | `1000` | Write `processed N rows` to stderr every N output rows. `0` disables progress. |
| `-semantic-cache` | `false` | Reuse RDAP responses for later IPs contained by the returned RDAP network range. |

## JSONL Output

Each successful row has this shape:

```json
{
  "row": 123,
  "prefix": "203.0.113.0/24",
  "queryIp": "203.0.113.0",
  "rir": "apnic",
  "bootstrapRir": "apnic",
  "finalRir": "apnic",
  "finalRdapHost": "rdap.apnic.net",
  "networkName": "EXAMPLE-NET"
}
```

Per-row failures are emitted to stdout as data, not just stderr:

```json
{
  "row": 456,
  "prefix": "198.51.100.0/24",
  "queryIp": "198.51.100.0",
  "error": "query RDAP for row 456 prefix 198.51.100.0/24: ..."
}
```

This lets partial runs remain analyzable even when individual RDAP endpoints fail.

## RIR Classification

The current classification is pragmatic:

1. `bootstrapRir` comes from the RDAP bootstrap answer URL.
2. `finalRir` and `finalRdapHost` come from the last successful RDAP HTTP response URL.
3. `rir` prefers `finalRir`, then `bootstrapRir`, then a weak fallback inferred from text in the returned RDAP network object.

RIR detection is string-based over known RDAP hostnames and related metadata. It is suitable for exploratory analysis, but should be audited before treating edge cases as authoritative.

## HTTP Transport

The RDAP client uses one shared `http.Client` for all lookups. The base transport is cloned from Go's `http.DefaultTransport` and then tuned from `-max-concurrent-rdap`:

- `MaxIdleConns = maxConcurrentRDAP * 4`
- `MaxIdleConnsPerHost = maxConcurrentRDAP`
- `MaxConnsPerHost = maxConcurrentRDAP`

The IANA RDAP bootstrap service should not be treated as the main throughput bottleneck. Bootstrap data is low-cardinality and cacheable. Sustained traffic fans out to the final RIR-specific RDAP hostnames, such as `rdap.apnic.net`, `rdap.arin.net`, `rdap.db.ripe.net`, and `rdap.lacnic.net`. The transport tuning is therefore mainly about keeping useful connections warm to those final RIR endpoints while keeping per-host concurrency explicit.

## Caches

### Exact HTTP Cache

`httpCacheTransport` wraps `github.com/kenshaw/diskcache`, which acts as an `http.RoundTripper` and caches GET responses on disk under `-cache-dir`.

- cache keys are derived from request method, scheme, host, path, and query
- cached files are gzip-compressed on disk
- only 2xx and 3xx responses are retained; non-success responses are evicted after fetch
- no full RDAP response bodies are retained in a process-wide memory map
- cache statistics are printed at process exit as disk hits and misses

This speeds repeated runs against the same RDAP URLs and avoids hammering RIR endpoints during iteration without causing long-running randomized jobs to grow an unbounded response-body map in RAM.

### Semantic Network Cache

When `-semantic-cache=true`, the command converts each returned RDAP network start/end range into covering prefixes and stores the RDAP result in an IP trie. Later prefixes whose query IP falls inside that network reuse the cached network and classification without making another RDAP call.

This is useful for speed. For presentation-grade `networkName` histograms, run with `-semantic-cache=false` unless you have checked that the cache does not hide more-specific RDAP network records for the sample being analyzed.

## Open Issues

### AFRINIC RDAP Reachability

AFRINIC RDAP lookups timed out repeatedly from one IPv6-only collection environment, while local or alternate paths could succeed for at least some test prefixes. This is currently an operational data-collection issue, not proof that AFRINIC lacks data.

Next steps:

- Test AFRINIC from IPv4-capable and dual-stack hosts.
- Record endpoint-specific timeout/error rates by RIR.
- Decide whether APNIC 62 charts should exclude AFRINIC, include AFRINIC with an explicit missingness caveat, or use a separately collected AFRINIC sample.

### No Resume Or Run Manifest

The command streams JSONL and progress logs but does not write a run manifest, status file, exit-code file, or checkpoint. Long remote jobs therefore need shell-side wrappers to preserve PID, command line, stdout, stderr, and exit status.

Next steps:

- Add a `-run-dir` option that writes stdout, stderr-compatible progress, arguments, start/end time, and exit code.
- Add resume support by skipping already emitted input rows or by accepting a completed-row ledger.

### RDAP Error Handling Is Minimal

Per-row errors are preserved, but there is no retry policy, no backoff, no per-RIR rate limiting, and no structured error classification.

Next steps:

- Classify timeout, bootstrap failure, HTTP status, decode error, and non-IP-network response separately.
- Add bounded retries for transient failures.
- Report error rates by RIR and final/bootstrap host.

### Semantic Cache Can Bias Detail-Oriented Analysis

The semantic cache assumes a returned RDAP network applies to every later query IP inside that range. That is often a useful speed optimization, but it can hide more-specific RDAP network records if an endpoint would have returned a narrower object for a different address in the range.

Next steps:

- Keep `-semantic-cache=false` for authoritative `networkName` and concentration measurements.
- Add a validation mode that samples cached hits and re-queries them to estimate cache-induced drift.

### Output Lacks Organization And Entity Fields

The current output captures `networkName`, but not RDAP entities, handles, organization names, country fields, notices, remarks, or event metadata. That limits analysis to network-name level rather than operator/entity level.

Next steps:

- Add optional entity extraction fields after deciding which RDAP roles are meaningful across RIRs.
- Keep raw RDAP cache available so new derived fields can be backfilled without re-querying every endpoint.

### More Test Coverage Needed

Initial tests cover RDAP network range-to-prefix conversion. The most important remaining untested logic is RIR classification from RDAP response URLs, final URL selection, streaming worker error-row behavior, and cache behavior.

Next steps:

- Add table tests for `rirFromURLString` and `finalRDAPURL`.
- Add a fake HTTP transport test for per-row RDAP failure preservation.

### Summaries Are External Scripts

The APNIC 62 CSV and Markdown views are currently produced by ad hoc scripts outside this command. The CLI itself only enriches rows.

Next steps:

- Either keep the CLI narrow and check in a separate summarizer, or add a second command dedicated to JSONL-to-view generation.
- Preserve the current review outputs as reproducible artifacts with commands and input labels.
